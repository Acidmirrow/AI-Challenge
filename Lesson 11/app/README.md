# Урок 11 — модель памяти ассистента

## Цель

Описать и реализовать модель памяти ассистента, разделённую на три слоя:

| Слой | Что хранит | Время жизни | Где хранится |
|---|---|---|---|
| **Краткосрочная** | Последние сообщения текущего диалога | TTL 24 ч; до 24 сообщений; в prompt — последние 8 | SQLite, `owner_id` + `session_id` |
| **Рабочая** | Задача, цель, статус, следующий шаг, ограничения | TTL 72 ч или до очистки | SQLite, `owner_id` + `session_id` |
| **Долговременная** | Профиль, решения, знания с `source` и `confidence` | профиль/решения — долго; знания — TTL | SQLite + FTS5, `owner_id` |

Главная идея: ассистент не должен смешивать «что мы обсуждали минуту назад», «что мы
делаем прямо сейчас» и «что мы знаем о пользователе и проекте постоянно».

## Как собирается контекст

Порядок фиксирован:

1. системная инструкция;
2. долговременная память — профиль, решения, знания;
3. рабочая память — текущая задача;
4. краткосрочная память — последние 8 сообщений;
5. сообщения диалога для модели.

Если слои противоречат друг другу, приоритет такой: рабочая память для текущей задачи,
краткосрочная — для последних договорённостей, долговременная — как справочный фон.
В prompt попадает только релевантная выборка долговременной памяти (FTS5 + профиль),
а не все записи; бюджет — около 900 токенов.

## Best practices

- у каждой записи есть слой, владелец (`owner_id`), источник и уверенность;
- краткосрочная и рабочая память ограничены TTL; знания получают TTL по умолчанию;
- точные факты хранятся в структурированных таблицах, FTS5 — только поисковый индекс;
- при обновлении факта предыдущая версия сохраняется в `long_term_history`;
- в контекст попадает релевантная выборка (`retrieve`) в пределах бюджета токенов, а не все
  записи;
- строки, похожие на секреты, отклоняются при записи;
- профиль и решения не удаляются при сбросе диалога, но могут быть удалены явно.

## API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/health` | статус, слои, TTL и лимит выборки |
| `GET` | `/api/model` | описание модели памяти и правил retrieval |
| `GET` | `/api/state` | состояние всех трёх слоёв |
| `GET` | `/api/context?q=...` | system prompt и релевантная выборка |
| `POST` | `/api/message` | добавить сообщение в краткосрочную память |
| `POST` | `/api/chat` | ответ модели с учётом всех слоёв + `question`, `system_prompt`, `messages`, `usage`, `request_tokens`, `response_tokens` |
| `POST` | `/api/chat/reset` | очистить краткосрочную и рабочую память |
| `DELETE` | `/api/short-term` | очистить краткосрочную память |
| `POST` | `/api/working` | сохранить рабочую задачу |
| `DELETE` | `/api/working` | очистить рабочую память |
| `POST` | `/api/long-term` | добавить/обновить запись с `source` и `confidence` |
| `DELETE` | `/api/long-term/{id}` | удалить запись долговременной памяти |

Параметр `session_id` по умолчанию — `demo`. Краткосрочная и рабочая память разделены
по сессиям; долговременная — общая для приложения.

## Facts урока 10

В долговременную память импортированы 16 facts из `facts_seed` задачи урока 10:
проект, бюджет, срок, локация, ответственный, ограничение, метрика, этапы, подрядчик,
договор, риск, резерв, отчётность, периодичность, приёмка и гарантия. Раздел — `knowledge`,
источник — `facts задачи дня 10`, confidence — `0.85`.

## UI

Вкладка **«Модель памяти ассистента (урок 11)»** в общем интерфейсе содержит:

- **Краткосрочная** — история диалога, поле ввода, кнопки «Отправить» и «Обогатить краткосрочную», сброс памяти;
- **Рабочая** — форма текущей задачи и кнопка «Обогатить рабочую память»;
- **Долговременная** — таблицы профиля, решений и знаний, кнопка «Обогатить долговременную память» и удаление записей;
- **Контекст** — реальный system prompt, который уходит модели;
- **Проверка** — кнопка «Запустить последовательную проверку»: сначала заполняет изолированный `demo-check` и задаёт вопрос при всех трёх слоях, затем по очереди восстанавливает демо-сессию, удаляет краткосрочную, рабочую и долговременную память по отдельности, задаёт тот же вопрос и сравнивает токены/ответы; в конце — таблица Δ и вывод о влиянии каждого слоя. Шага 2 (сброс + повторный вопрос) больше нет. Для показа: `/?showcase=1`.
- На каждой вкладке — компактная строка «Сейчас в памяти» с текущим содержимым слоя.
- Над вкладками — информационный блок «Где хранятся слои памяти»: SQLite-таблицы, TTL, FTS5, путь к базе; промт не хранится и собирается заново.
- В сценарии проверки показываются чат, отправленный system prompt и полученный ответ.
- В системном промте каждый слой получает явный статус; пустой слой помечается «пусто» / «сведений не найдено», и модель обязана указать это в начале ответа.
- После отправки — компактная таблица «Что попало в промт» с токенами по слоям и единым блоком «Промт запроса / Промт ответа».
- Поле ввода предзаполняется дефолтным промтом по трём слоям и не отправляется автоматически.
- API отдаёт `Cache-Control: no-store`; фронт запрашивает состояние заново при каждом rerun.

В сайдбаре — счётчики слоёв и кнопка «Сбросить диалог и задачу». Долговременная память
при этом сохраняется. Демонстрационное видео: `~/Movies/Lesson 11.mp4` — screencast только UI, 1440×1000, ~18 с.

## Запуск

В общем стеке курса:

```bash
docker compose up -d --build
open http://localhost:8500        # раздел «Модель памяти ассистента (урок 11)»
```

API через шлюз: `http://localhost:8000/lesson-11/api/health`.

Изолированно:

```bash
cd "Lesson 11/app"
docker compose up -d --build
open http://localhost:8511        # UI
curl http://localhost:8011/api/health
```

Порты изолированного запуска: UI `8511`, API `8011`. Их можно переопределить через
`API_PORT` и `FRONT_PORT`.

## Конфигурация

- `MEMORY_DB_PATH` — путь к SQLite; по умолчанию `/srv/data/memory.db`.
- `OPENCODE_GO_MODEL` — модель чата; по умолчанию `deepseek-v4.1-flash`.
- `OPENCODE_GO_PRO_MODEL` — модель анализа; по умолчанию `deepseek-v4-pro`.
- Ключ OpenCode Go берётся из `Lesson 06/app/config/secrets.properties` (gitignored)
  или из `OPENCODE_GO_API_KEY`; в репозиторий не попадает.
- В `Lesson 11/app/data/` лежит только локальная база, она исключена из git.

## Тесты

```bash
cd "Lesson 11/app"
docker compose run --rm api python -m pytest -q
```

Проверяются:

- наличие трёх слоёв и их описание;
- стартовые записи долговременной памяти с provenance;
- ограничение, TTL и очистка краткосрочной памяти;
- изоляция рабочей памяти по сессиям;
- обновление записи по ключу без дубликата и история конфликта;
- изоляция долговременной памяти по владельцу;
- релевантная выборка вместо всей памяти и сборка контекста;
- отказ при попытке записать секрет;
- сохранение долговременной памяти при сбросе и перезапуске;
- ответ чата с учётом памяти.

Текущий результат: **16 passed**.

## Что сознательно не реализовано

- Векторный поиск и эмбеддинги: долговременная память читается целиком.
- Многопользовательская авторизация: `session_id` — учебный идентификатор, не аккаунт.
- Автоматическое извлечение фактов из диалога: записи добавляются через UI или API.
- TTL для долговременной памяти: профиль, решения и знания не истекают автоматически.
