# Урок 13 · Состояние задачи (Task state machine)

## Цель

Показать, что состояние задачи — это формальный конечный автомат, а не текст в
промпте. Переходы проверяются сервером, LLM не может перепрыгнуть этап, а UI
отображает текущий шаг, ожидаемое действие и историю.

## Жизненный цикл

```text
planning → execution → validation → done
```

Правила:

- реализация начинается только после утверждения плана;
- валидация начинается только после завершения реализации;
- завершение доступно только после успешной валидации;
- при провале валидации возможна доработка `validation → execution`;
- при `rework` сбрасываются флаги реализации и валидации;
- пауза не меняет этап и разрешает только продолжение.

## Что реализовано

- отдельное приложение `Lesson 13/app` с FastAPI и Streamlit;
- отдельный маршрут шлюза `/lesson-13/api/*`;
- пункт меню **«Состояние задачи (Task state machine) (урок 13)»** в неделе 3;
- SQLite-хранилище `Lesson 13/app/data/lesson13.db`;
- доменный автомат без зависимостей от FastAPI и UI;
- API создания, переходов, паузы, продолжения и истории;
- проверка `version` и защита от гонок;
- структурированные ошибки `guard_failed`, `transition_not_allowed`,
  `task_paused`, `version_conflict`;
- UI со stepper, флагами, доступными действиями и историей;
- чат получает снимок состояния, но не меняет его.

## API

Все запросы к задаче требуют `X-Session-Id`.

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/health` | `state_machine: available` |
| `POST` | `/api/task` | создать задачу |
| `GET` | `/api/task` | текущее состояние |
| `POST` | `/api/task/transition` | действие с проверкой guards |
| `POST` | `/api/task/pause` | пауза |
| `POST` | `/api/task/resume` | продолжение |
| `GET` | `/api/task/history` | история переходов и отказов |
| `GET` | `/api/task/log` | журнал работы агента |
| `GET` | `/api/task/steps` | шаги реализации и прогресс |
| `POST` | `/api/task/step` | выполнить следующий шаг плана |
| `POST` | `/api/task/clarify` | уточняющие вопросы в чате или план после ответов |
| `POST` | `/api/chat` | чат с контекстом задачи |
| `GET` | `/api/chat/history` | история чата текущей задачи |
| `POST` | `/api/chat/message` | сохранить сообщение/команду в историю |

Пример:

```json
{
  "action": "start_execution",
  "reason": "План утверждён",
  "version": 3
}
```

## UI

В общем интерфейсе — раздел **«Состояние задачи (Task state machine) (урок 13)»**.
Изолированный фронт — `http://localhost:8513`.

На экране:

- одно поле ввода: обычный вопрос — чат, `/gotask <цель>` — постановка задачи;
- отправка сообщения по Enter или кнопке «Отправить»; поле ввода находится под окном чата;
- план передаётся в следующие этапы и по умолчанию скрыт в expander «План задачи»;
- переключатель «Разрешить агенту интернет»: результаты поиска как факты, без ссылок в ответе;
- вкладка «Лог агента» с запросами, переходами, поиском и ошибками;
- после `/gotask` задача создаётся и сразу получает первый ответ ассистента;
- визуализация показывается только при наличии задачи;
- горизонтальный stepper из четырёх этапов;
- текущий шаг и ожидаемое действие;
- версия состояния и флаги плана/реализации/валидации;
- управление только командами в чате: `/approve`, `/start`, `/validate`, `/pass`, `/fail`, `/rework`, `/pause`, `/resume`;
- пауза/продолжение;
- история переходов и отказов;
- чат по задаче только во вкладке «Состояние задачи»;
- вкладка «Лог агента» без чата;
- история чата, запросов и задач сохраняется в SQLite и восстанавливается после обновления страницы;
- результаты шагов — в свёрнутых expander, план — тоже скрыт по умолчанию;
- в сайдбаре — очистка задач и чата с подтверждением.

## Проверка

```bash
cd "Lesson 13/app"
docker compose up -d --build
curl http://localhost:8013/api/health
docker compose -f "Lesson 13/app/docker-compose.yml" run --rm api python -m pytest -q
```

Ожидаемый результат: **29 passed**.

Ручной сценарий:

1. Отправить `/gotask <цель>` в поле чата.
2. Ответить на выделенные уточняющие вопросы; план появится в свёрнутом expander.
3. Отправить `/approve`; дождаться 10-секундного отсчёта и старта реализации.
4. Шаги выполняются автоматически; результаты — в expander каждого шага, процесс можно остановить и продолжить.
5. После последнего шага дождаться интерактивного 10-секундного отсчёта — валидация запустится автоматически.
6. Отправить `/pass` (или `/fail`); при `/pass` задача сразу переходит в «Готово».
7. Проверить, что stepper показывает все этапы пройденными.
8. Поставить задачу на паузу и убедиться, что переходы заблокированы.


## Контекст до постановки задачи

План или требования, написанные в чате до `/gotask`, передаются планировщику
и сохраняются за задачей. В новый чат переносятся только сообщения пользователя,
чтобы не смешивать старые ответы ассистента с новым состоянием.


## Тестовое задание

Кнопка «🧪 Тестовое задание: 5 событий 1969 года» создаёт короткую задачу
с планом из трёх шагов; задача проходит планирование и ожидает утверждения. Это удобно для проверки
всего цикла без ручного ввода цели.
