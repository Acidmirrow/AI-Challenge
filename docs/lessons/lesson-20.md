# Урок 20 — Оркестрация MCP

## Цель

Собрать несколько MCP-серверов в одном приложении, дать агенту общий каталог
инструментов, маршрутизировать вызовы по серверам и сохранить работоспособность
при падении одного соединения.

```text
orders (свой) ─┐
analytics (свой) ├─→ MCPHub → агент
time (внешний) ─┘
```

## Серверы и инструменты

| Сервер | Тип | Инструменты |
|---|---|---|
| `lesson20-orders` | собственный stdio | `get_customer`, `get_status`, `create_order` |
| `lesson20-analytics` | собственный stdio | `forecast`, `get_status` |
| `mcp-server-time` | внешний reference-сервер | `get_current_time`, `convert_time` |

`get_status` есть на двух серверах. Хаб разрешает коллизию именами
`orders__get_status` и `analytics__get_status`; маршрут хранит исходное имя и
сервер. Внешний Time-сервер подключается как зависимость `mcp-server-time`.

## Как работает

- `hub.py` открывает все stdio-соединения через `AsyncExitStack`, получает
  `tools/list` с каждого сервера и собирает единый каталог.
- `tool_schemas()` отдаёт модели имена с префиксами только при коллизии.
- `hub.call()` находит соединение по имени инструмента и вызывает исходный tool
  на нужном сервере.
- `MCPHub` закрывает все соединения в `__aexit__` даже при ошибке одного сервера.
- Недоступный сервер попадает в `failures`, остальные серверы и инструменты
  продолжают работать.
- `MultiMCPChat` передаёт агенту агрегированные схемы, выполняет вызовы и
  возвращает трассу с `server`, `original` и результатом.
- `flow.py` выполняет длинный детерминированный флоу:
  клиент → прогноз → статус аналитики → статус заказов → текущее время.

## Отказ сервера

В UI можно отметить сервер как недоступный. В запросе это передаётся как
`disabled_servers: ["time"]`.

- остальные серверы подключаются и отдают инструменты;
- в системном сообщении агент видит список недоступных серверов;
- если нужен инструмент недоступного сервера, агент сообщает об этом и не
  выдумывает данные;
- длинный флоу останавливается ровно на шаге недоступного сервера, сохраняя
  выполненные шаги и причину.

## API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/health` | состояние и число серверов |
| `GET` | `/api/models` | модели агента |
| `POST` | `/api/mcp/inspect` | соединения, агрегированный каталог и ошибки |
| `POST` | `/api/flow/run` | длинный флоу с `disabled_servers` |
| `POST` | `/api/chat` | агентский чат с инструментами всех серверов |

## Запуск

Общий UI: `http://localhost:8500`, раздел «Оркестрация MCP (урок 20)».
API через шлюз: `http://localhost:8000/lesson-20/api/*`.

Изолированно:

```bash
docker compose -f "Lesson 20/app/docker-compose.yml" up -d --build
```

API `8020`, UI `8520`.

## Проверка

```bash
curl http://localhost:8020/api/health
curl -X POST http://localhost:8020/api/flow/run \
  -H 'Content-Type: application/json' \
  -d '{"customer_id":"C-104","amount_rub":100000,"disabled_servers":[]}'
```

Тесты: **5 passed**. Они проверяют три соединения, коллизии имён, длинный флоу
по трём серверам, отключение Time-сервера при работающих остальных и агентскую
маршрутизацию с недоступным сервером.
