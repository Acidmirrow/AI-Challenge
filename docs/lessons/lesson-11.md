# Урок 11 — модель памяти ассистента

## Цель урока

Показать, что «память ассистента» — это не один список сообщений, а несколько слоёв с
разным временем жизни и разным назначением. В уроке реализованы:

1. **Краткосрочная память** — текущий диалог.
2. **Рабочая память** — данные текущей задачи.
3. **Долговременная память** — профиль, решения и знания.

## Три слоя

| Слой | Вопрос, на который отвечает | Примеры | Ограничение |
|---|---|---|---|
| Краткосрочная | «Что мы только что обсуждали?» | последние реплики, уточнения | TTL 24 ч; 24 сообщения; в prompt — 8 |
| Рабочая | «Что мы делаем прямо сейчас?» | задача, цель, статус, следующий шаг, ограничения | TTL 72 ч; одна активная задача на сессию |
| Долговременная | «Что мы знаем о пользователе и проекте?» | имя, роль, предпочтения, решения, знания | `source` + `confidence`; TTL знаний; FTS5-выборка |

Краткосрочная и рабочая память привязаны к `session_id`; долговременная — глобальная.

## Сборка контекста

```
system prompt
  ├── долговременная память: профиль / решения / знания
  ├── рабочая память: задача / цель / статус / следующий шаг / ограничения
  └── краткосрочная память: последние 8 сообщений
        ↓
     сообщения для модели
```

При конфликте слоёв приоритет: рабочая память → краткосрочная → долговременная как
справочный фон. В prompt уходит только релевантная выборка долговременной памяти, а не
все записи; найденная память считается данными, а не инструкцией.

## Реализация

- API: FastAPI, `Lesson 11/app/api/app/main.py`.
- Модель памяти: `memory.py`, класс `MemoryStore`.
- Сборка prompt: `context.py`.
- Модель: `deepseek-v4.1-flash` из OpenCode Go через `llm.py`; анализ — `deepseek-v4-pro`.
- Хранение: SQLite `Lesson 11/app/data/memory.db` (не коммитится), FTS5, `owner_id`, TTL,
  provenance и confidence.
- UI: отдельная вкладка в общем front и отдельный front урока 11.

### Основные endpoint'ы

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/api/model` | описание трёх слоёв |
| `GET` | `/api/state` | текущее состояние памяти |
| `GET` | `/api/context` | собранный system prompt |
| `POST` | `/api/chat` | ответ модели с учётом памяти |
| `POST` | `/api/working` | сохранить текущую задачу |
| `POST` | `/api/long-term` | запомнить профиль/решение/знание |
| `DELETE` | `/api/long-term/{id}` | удалить запись |
| `POST` | `/api/chat/reset` | очистить краткосрочную и рабочую память |

## Facts урока 10

В долговременную память добавлены 16 facts из текущей задачи урока 10
(`/lesson-10/api/generate`, `facts_seed`): проект, бюджет, срок, локация, ответственный,
ограничение, метрика, этапы, подрядчик, договор, риск, резерв, отчётность, периодичность,
приёмка и гарантия. Они записаны в раздел `knowledge` с источником
`facts задачи дня 10` и `confidence=0.85`.

## UI

Раздел **«Модель памяти ассистента (урок 11)»**:

- карточки трёх слоёв со счётчиками;
- вкладка краткосрочной памяти с чатом;
- вкладка рабочей задачи с формой;
- вкладка долговременной памяти с таблицами и добавлением записей;
- вкладка «Контекст» с реальным prompt, который уходит модели;
- на вкладках краткосрочной, рабочей и долговременной памяти — компактная строка «Сейчас в памяти»;
- отдельные кнопки обогащения: «Обогатить краткосрочную», «Обогатить рабочую память», «Обогатить долговременную память»;
- кнопка «Сбросить краткосрочную память»;
- информационный блок «Где хранятся слои памяти»: SQLite-таблицы, TTL, FTS5 и путь к базе;
- вкладка «Проверка» с одним последовательным запуском: сначала вопрос при всех трёх слоях, затем удаление слоёв по одному; в сценарии видны чат, отправленный system prompt и полученный ответ;
- шаг 2 (сброс краткосрочной и рабочей + повторный вопрос) удалён;
- для каждого слоя отдельно восстанавливается демо-сессия, удаляется только он, задаётся тот же вопрос и сравниваются токены/ответы; итоговая таблица показывает Δ и влияние удаления;
- режим показа `/?showcase=1` скрывает навигацию и лишний текст, оставляя сценарий, таблицы и метрики;
- ответы API с `Cache-Control: no-store`, фронт не использует `st.cache_data` и перечитывает состояние;
- system prompt явно маркирует пустые слои и требует от модели перечислять их состояние в начале ответа.
- после отправки — компактная таблица «Что попало в промт» с токенами по слоям;
- единый показ «Промт запроса: N токенов · Промт ответа: M токенов»; при наличии используется `usage` модели;
- поле ввода предзаполняется дефолтным промтом по трём слоям, но не отправляется автоматически.

Кнопка «Сбросить диалог и задачу» очищает краткосрочную и рабочую память, но **не**
удаляет долговременную.

## Запуск

В общем стеке:

```bash
docker compose up -d --build
open http://localhost:8500
```

Изолированно:

```bash
cd "Lesson 11/app"
docker compose up -d --build
open http://localhost:8511
```

Порты: API `8011`, UI `8511`. В общем стеке API доступен как
`http://localhost:8000/lesson-11/api/...`.

## Тесты

```bash
cd "Lesson 11/app"
docker compose run --rm api python -m pytest -q
```

**16 passed** — проверяются три слоя, TTL и ограничение краткосрочной памяти, изоляция
рабочей задачи и владельца, история конфликтов, релевантная выборка, отказ при записи
секрета, сборка контекста, сброс и ответ чата.

## Ограничения урока

Урок намеренно не использует векторную базу, эмбеддинги и автоматическое извлечение
фактов. Это делает механику памяти прозрачной: видно, какие именно записи попадают в
контекст и почему. Векторный поиск, TTL и авторизация — возможные следующие шаги.
