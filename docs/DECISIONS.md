# Журнал принятых решений

Журнал фиксирует **согласованные** архитектурные, продуктовые и рабочие решения проекта.
Правило: решения не переписываются задним числом; при изменении статуса старая запись
помечается как `заменено` или `отменено` со ссылкой на новое решение.

## Как вести журнал

- Новое решение добавляется отдельной записью в конец файла и строкой в индекс.
- В записи указываются: дата, статус, контекст, решение, рассмотренные альтернативы и последствия.
- Секреты, ключи и значения из `secrets.properties` / `.env` в журнал не попадают.
- Если решение меняется, старая запись не удаляется: у неё меняется статус и появляется ссылка.
- При завершении урока проверяем, появились ли новые решения, и дополняем журнал.

## DEC-001 · Изоляция уроков

**Дата:** 2026-11-16 · **Статус:** принято

**Контекст.** Курс растёт от одного чата до десяти самостоятельных лабораторий; изменения
одного урока не должны ломать остальные.

**Решение.** Каждый урок — отдельное приложение FastAPI + Streamlit в `Lesson 0X/app/`
со своими `api/`, `front/`, `config/`, тестами и `docker-compose.yml`. Общий корневой
`docker-compose.yml`, gateway и front только собирают и публикуют приложения. Повторение
кода между уроками считается допустимым.

**Альтернативы.** Единый монолит с общими библиотеками; общий пакет компонентов.

**Последствия.** Больше дублирования и правок при изменении общего UI, зато уроки можно
запускать и проверять независимо, а учебный код остаётся наглядным.

## DEC-002 · Секреты вне репозитория

**Дата:** 2026-11-16 · **Статус:** принято

**Контекст.** Проект использует ключи DeepSeek, OpenRouter, Nous Portal, Gemini и других
провайдеров.

**Решение.** Секреты хранятся только в gitignored `Lesson 0X/app/config/secrets.properties`
или в `~/.hermes/.env` с правами `600`. В git попадают только примеры без значений. Ключи
не выводятся в чат и не коммитятся.

**Альтернативы.** Хардкод в `app.properties`; передача ключей через compose-файл.

**Последствия.** Локальная настройка требует ручного заполнения секретов; зато утечка через
git исключена.

## DEC-003 · Провайдеры и модели

**Дата:** 2026-11-16 · **Статус:** заменено (DEC-014)

**Контекст.** Нужны стабильные ответы для уроков и отдельная более сильная модель для
итогового анализа.

**Решение.** Основной провайдер — DeepSeek. `deepseek-flash` используется для чата и
повседневных запросов, `deepseek-v4-pro` — только для формирования результатов и
развёрнутого анализа. Бесплатные провайдеры подключаются только с моделями `:free` и
стоимостью `0`. Новый провайдер или смена модели согласуются с пользователем. Grok/Groq
не используются.

**Альтернативы.** OpenRouter, Gemini, Nous Portal как основные; локальные заглушки.

**Последствия.** Есть стоимость у DeepSeek, но предсказуемое качество; бесплатные
провайдеры остаются резервными.

## DEC-004 · Структура диалога урока 10

**Дата:** 2026-11-16 · **Статус:** принято

**Контекст.** Нужно сравнить стратегии контекста на одинаковой истории, а не на разных
диалогах.

**Решение.** Общий ствол — 25 уникальных сообщений. От точки №25 расходятся три ветки по
10–15 сообщений; первое сообщение каждой ветки имеет `id = 26`. В диалоге сохраняются
`branch_point = 25`, `trunk_hash` и Checkpoints (старт, 10, 20, точка ветвления, начало и
конец ветки).

**Альтернативы.** Три независимых диалога; разная длина ствола для каждой ветки.

**Последствия.** Стратегии сравниваются на идентичном префиксе; ветки визуально и
программно отделены от ствола.

## DEC-005 · Автоматический размер Sliding window

**Дата:** 2026-11-16 · **Статус:** принято

**Контекст.** Фиксированное окно отрезало часть выбранной ветки, из-за чего сравнение
стратегий становилось нечестным.

**Решение.** Sliding window включает **10 последних сообщений ствола + все сообщения
выбранной ветки**: `N = 10 + len(branch)`. Полная история — весь ствол плюс выбранная
ветка.

**Альтернативы.** Фиксированные N сообщений; только последние N без привязки к ветке.

**Последствия.** Ветка всегда представлена целиком, ствол — компактным контекстом;
размер окна меняется вместе с длиной ветки.

## DEC-006 · Развёрнутый анализ

**Дата:** 2026-11-16 · **Статус:** принято

**Контекст.** Синхронный вызов `deepseek-v4-pro` внутри async endpoint блокировал API,
переключение ветки падало с `ReadTimeout`, а пустой ответ мог закэшироваться.

**Решение.** Анализ запускается только кнопкой «Сформировать развёрнутый вывод», выполняется
в threadpool, кэшируется по ветке и не запускается при переключении ветки. Для Pro
`max_tokens = 4000`; пустой ответ не кэшируется. В payload передаются только сводные
параметры стратегий.

**Альтернативы.** Автоматический анализ при каждом переключении; синхронный вызов в
event loop.

**Последствия.** Ожидание анализа ~45–50 секунд, но API остаётся отзывчивым, а повторный
просмотр ветки не тратит токены.

## DEC-007 · Чат до и после генерации

**Дата:** 2026-11-16 · **Статус:** принято

**Контекст.** Пользовательские сообщения должны получать ответ модели, но полный
сгенерированный диалог не должен появляться от одного ввода в поле.

**Решение.** Сообщение в окне ввода отправляется модели и сохраняется вместе с ответом.
Полная генерация диалога — только по кнопке «Сгенерировать диалог». Сообщения, отправленные
до генерации, сохраняются и добавляются **перед** сгенерированным диалогом. После генерации
рядом с «Отправить» есть переключатель «Только по контексту» / общий вопрос модели.

**Альтернативы.** Автогенерация при вводе; локальная заглушка вместо ответа модели.

**Последствия.** Пользователь контролирует момент генерации; pre-chat не теряется и не
смешивается с ветками.

## DEC-008 · Уникальность диалога

**Дата:** 2026-11-16 · **Статус:** принято

**Контекст.** Одинаковые вопросы в трёх ветках и повторяющиеся сообщения мешали понять,
к какой ветке относится реплика.

**Решение.** Сообщения ствола и веток не повторяются. У каждой ветки свой набор
формулировок вопросов, привязанный к её смыслу, а не только к названию. Уникальность
проверяется тестом.

**Альтернативы.** Общие шаблоны с подстановкой названия ветки; добавление префикса только
к ответам.

**Последствия.** Диалог легче читать и отлаживать; при добавлении ветки нужно писать
отдельные вопросы.

## DEC-010 · Git-процесс

**Дата:** 2026-11-16 · **Статус:** принято

**Контекст.** Проект учебный, но история коммитов должна оставаться понятной.

**Решение.** Не коммитить и не пушить автоматически. Коммит выполняется только по явной

**Последствия.** Пользователь контролирует историю; перед коммитом нужно явно попросить
разрешение.

## DEC-013 · Модель памяти урока 11

**Дата:** 2026-11-16 · **Статус:** принято

**Контекст.** Нужен отдельный урок, который не только описывает, но и показывает работу
памяти ассистента: что хранится в текущем диалоге, что относится к задаче, а что должно
переживать перезапуск.

**Решение.** Ввести три слоя памяти:

- **краткосрочная** — последние сообщения текущего диалога, лимит 24, в prompt уходят
  последние 8;
- **рабочая** — задача, цель, статус, следующий шаг и ограничения текущей сессии;
- **долговременная** — профиль, решения и знания, глобальные для приложения.

Краткосрочная и рабочая память привязаны к `session_id` и хранятся в SQLite вместе с
долговременной. Долговременная память не очищается кнопкой сброса диалога. Контекст
собирается в порядке: system prompt → долговременная → рабочая → краткосрочная →
сообщения. Чат использует `deepseek-v4.1-flash` из OpenCode Go; урок оформлен отдельным приложением
`Lesson 11/app` с API, front, тестами и вкладкой в общем UI.

**Альтернативы.** Единый JSON-файл памяти; только in-memory хранение; векторная память с
эмбеддингами; одна общая история без разделения слоёв.

**Последствия.** Долговременная память переживает перезапуск, краткосрочная остаётся
ограниченной и дешёвой, рабочая не смешивается с профилем. Векторного поиска и
многопользовательской авторизации в уроке нет — это следующие темы, а не скрытая часть
текущей реализации.

## DEC-014 · OpenCode Go как провайдер UI

**Дата:** 2026-11-16 · **Статус:** принято

**Контекст.** У пользователя есть подписка OpenCode Go; нужно использовать её для общения
в UI и для анализа, не смешивая с прямым API DeepSeek и не передавая ключ в git.

**Решение.** Основной провайдер учебного UI — `opencode-go`:

- чат: `deepseek-v4.1-flash`;
- анализ: `deepseek-v4-pro`;
- base URL: `https://opencode.ai/zen/go/v1`;
- обязательный заголовок `x-opencode-session`;
- ключ хранится только в gitignored `Lesson 0X/app/config/secrets.properties` как
  `opencode_go.api.key` (и в `~/.hermes/.env` для Hermes);
- уроки 01–07 получают провайдера через общий каталог моделей, уроки 09–11 — через
  собственные клиенты, использующие те же id;
- для подписки стоимость прогона считается нулевой с пояснением «входит в подписку».

Прямой DeepSeek остаётся доступным как явная альтернатива в конфигурации, но не является
провайдером по умолчанию.

**Альтернативы.** Оставить прямой DeepSeek; перейти на OpenRouter; настроить провайдера
только в одном уроке.

**Последствия.** UI зависит от лимитов подписки OpenCode Go; модели и заголовок сессии
нельзя менять без проверки. Зато чат и анализ используют один оплаченный канал, а ключ
не попадает в репозиторий.

**Дата:** 2026-11-16 · **Статус:** принято

**Контекст.** Курс будет состоять из пяти недель по пять уроков; текущая навигация
показывала только недели с уже добавленными материалами и не масштабировалась.

**Решение.** Навигация фиксирует пять недель: 01–05, 06–10, 11–15, 16–20, 21–25.
В сайдбаре показываются пять компактных переключателей `1…5` в одну строку без переноса.
Недели без материалов показывают заглушку «уроки ещё не добавлены»; текущая неделя
определяется по последнему добавленному уроку.

**Альтернативы.** Показывать только непустые недели; вертикальный список недель; скрывать
будущие недели до появления уроков.

**Последствия.** Пользователь сразу видит горизонт курса, а пустые недели не ломают
навигацию. При добавлении уроков 12–25 достаточно расширять `SECTIONS`, не меняя вёрстку
переключателя.

## DEC-016 · Memory Guardian и bad-practice правила

**Дата:** 2026-11-16 · **Статус:** принято

**Контекст.** Память агента легко превращается в свалку: один vector store, записи без
источника, общий профиль, вечная история и retrieval без проверки прав. Нужны явные
анти-паттерны и отдельная точка контроля.

**Решение.** Зафиксировать bad-practice правила R-004–R-013 в `docs/RULES.md` и ввести
роль **Memory Guardian** (`docs/ROLES.md`). Guardian проверяет слои, источник истины,
provenance, изоляцию, TTL/конфликты, бюджет контекста, PII, процедурные изменения и
доверие к retrieval. Изменение памяти без `MEMORY REVIEW: PASS` не считается завершённым.

**Альтернативы.** Полагаться на общие best practices без формальных правил; проверять
память только на code review; оставить контроль автору изменения.

**Последствия.** Появляется дополнительный шаг ревью для memory-изменений, зато ошибки
памяти не накапливаются незаметно. Роль не выбирает продукт за пользователя и не заменяет
архитектурные решения — она проверяет соблюдение правил.

## DEC-017 · Best-practice реализация памяти

**Дата:** 2026-11-16 · **Статус:** принято

**Контекст.** Для урока 11 нужно реализовать три слоя памяти по правилам R-004–R-013,
не превращая учебный проект в инфраструктурный полигон.

**Решение.** Использовать SQLite + FTS5:

- структурированные записи вместо хранения фактов только в векторах;
- `owner_id` и `session_id` для изоляции;
- TTL для краткосрочной/рабочей памяти и знаний;
- `source`, `confidence`, `importance`, `status`;
- историю заменённых значений при конфликте;
- FTS5 + профиль + confidence/recency/importance для ограниченной выборки;
- отказ при записи строк, похожих на секреты.

Дополнительный Docker-сервис (Postgres/pgvector/Redis) на этом объёме не требуется.
При росте до нескольких пользователей/большого корпуса знаний — миграция на Postgres +
pgvector и Redis для рабочей памяти.

**Альтернативы.** Postgres + pgvector сразу; Redis + vector DB; хранить всё в JSON.

**Последствия.** Решение прозрачное, тестируемое и дешёвое. Ограничения: нет
аутентификации, шифрования at-rest и семантических эмбеддингов; для production их нужно
добавить до работы с реальными PII.

## DEC-018 · Токены запроса/ответа и дефолтный промт

**Дата:** 2026-11-16 · **Статус:** принято

**Контекст.** В чате урока 11 токены отображались непоследовательно, а пустое поле ввода
не показывало, что бэкенд собирает все три слоя памяти. При этом устаревший статус рабочей
памяти мог привести к ложному выводу «работа не сдвинулась».

**Решение.** Для каждого ответа показывать единый блок
«Промт запроса: N токенов · Промт ответа: M токенов». Использовать фактический `usage`
OpenCode Go, при его отсутствии — оценку. После ответа показывать компактную таблицу
«Что попало в промт» по слоям. Поле ввода предзаполнять дефолтным промтом, который
содержит сведения из всех трёх слоёв, но не отправлять его без действия пользователя.
Статус рабочей памяти не считать доказательством прогресса проекта.

**Альтернативы.** Показывать только общий расход; показывать токены лишь в контекстной
вкладке; оставить поле пустым.

**Последствия.** Пользователь видит цену запроса и состав контекста до/после отправки,
а формулировки модели меньше зависят от одного устаревшего поля.

## DEC-019 · Компактные срезы памяти и раздельное обогащение слоёв

**Дата:** 2026-11-16 · **Статус:** принято

**Контекст.** На вкладках памяти были видны формы и таблицы, но не было короткого ответа
«что сейчас лежит в этом слое». Одно поле ввода смешивало запрос к модели и добавление
реплики, а данные могли выглядеть устаревшими после действий.

**Решение.** На каждой вкладке показывать строку «Сейчас в памяти» с текущим содержимым.
Разделить действия: «Обогатить краткосрочную» добавляет реплику без вызова модели,
«Обогатить рабочую память» сохраняет задачу, «Обогатить долговременную память» сохраняет
факт. Кнопка очистки краткосрочной называется «Сбросить краткосрочную память». API отдаёт
`Cache-Control: no-store`; фронт не использует `st.cache_data` и перечитывает состояние.

**Последствия.** Пользователь видит актуальный срез без лишних переходов и понимает,
какой слой обогащает каждая кнопка.

## DEC-020 · Явный статус пустых слоёв памяти

**Дата:** 2026-11-16 · **Статус:** принято

**Контекст.** Модель могла молча пропустить слой, в котором не было данных, и ответ
выглядел так, будто анализ трёх слоёв был полным.

**Решение.** В system prompt всегда включать статус каждого слоя: «пусто», «сведений
не найдено» или перечень найденного. Модель обязана начинать анализ с состояния всех
трёх слоёв и не пропускать пустые. API также возвращает `empty` и `status` для каждого
слоя.

**Последствия.** Пользователь видит, что именно проверено и где памяти не хватило,
вместо правдоподобного ответа без источника.

## DEC-021 · Наглядная проверка урока 11

## DEC-022 · Где хранятся слои и что видно в демо

## DEC-024 · Только шаги 1 и 3, последовательно

## DEC-030 · Целостность ответов, код и границы ролей

**Дата:** 2026-11-17 · **Статус:** принято

**Контекст.** Прогон 10 вопросов показал обрывы ответов, несоответствие требования
«с примерами кода» фактическому тексту и нечёткие границы ролей: профили отвечали

**Решение.**

  признаках обрыва выполняется до двух продолжений с места обрыва.
- Profile Store и system prompt проверяют требование «с примерами кода»: для дизайнера

- Имя профиля запрещено использовать как обращение к пользователю.
- Анализ Pro дополнительно оценивает соблюдение границ роли и наличие кода.

**Последствия.** Ответы проверки должны быть завершёнными и соответствовать
заявленному профилю; нарушения видны в UI и в анализе.

**Решение.** Добавить в урок 13 подключаемый доменный автомат:
`planning → execution → validation → done`. Хранить состояние и историю в SQLite,
проверять guards и `version` на сервере, сделать действия `submit_plan`,
`approve_plan`, `start_execution`, `complete_execution`, `start_validation`,
`pass_validation`, `fail_validation`, `finish`, `rework`, `pause`, `resume`.
При `rework` сбрасывать флаги реализации и валидации. UI показывает stepper,
текущий шаг, ожидаемое действие, флаги и только доступные действия; чат получает
снимок состояния, но не меняет его.

**Последствия.** Переход нельзя обойти текстом или кнопкой UI без серверной
проверки; состояние переживает перезапуск; история отказов доступна для аудита.


## DEC-035 · Урок 13: единый ввод и интернет для агента

**Решение.** Оставить одно поле: обычный текст уходит в чат, `/gotask <цель>`

«Разрешить агенту интернет»; при включении сервер делает keyless веб-поиск,

**Последствия.** На экране одно основное окно ввода; интернет включается явно и

## DEC-036 · Лог агента и блокирующие ошибки

**Дата:** 2026-11-17 · **Статус:** принято

**Контекст.** Переходы и чат уже работали, но причина сбоя была видна только в

ассистента не запрашивался.

**Решение.** После `/gotask` сразу запрашивать первый ответ ассистента. Добавить

## DEC-037 · Автоматический план и явная передача между этапами

**Дата:** 2026-11-17 · **Статус:** принято

**Контекст.** После `/gotask` ассистент предлагал план, но задавал уточняющие
вопросы. План не был обязательным состоянием задачи и мог не попасть в
следующие этапы.

**Решение.** Добавить `POST /api/task/plan`: сервер сам формирует план по цели,
не задавая вопросов, сохраняет `plan_text` в задаче и переводит её в состояние
«план отправлен». Если модель вернула вопросы или недоступна, используется
локальный план. UI сразу показывает план и передаёт его в контекст чата,
реализации и валидации через снимок состояния.

**Последствия.** Пользователь не вводит план вручную и не отвечает на вопросы
планировщика; план является явным полем задачи и доступен на всех следующих
этапах.


## DEC-038 · Уточнения в чате перед планом, без допущений

**Дата:** 2026-11-18 · **Статус:** принято

**Контекст.** Автоматический план мог строиться по неполной постановке и
содержать допущения. Пользователь должен видеть уточняющие вопросы и отвечать
на них в том же чате; постановка плана тоже должна происходить через чат.

**Решение.** `POST /api/task/clarify` анализирует цель и историю диалога. Если
данных не хватает, он возвращает 1–5 вопросов и не меняет состояние задачи;
вопросы выводятся в чате выделенным блоком. После ответов пользователя тот же
endpoint формирует план, сохраняет его в `plan_text` и переводит задачу в
«план отправлен». Планировщику запрещено придумывать факты и использовать
допущения; при недоступности модели показываются вопросы/ошибка, а не
фиктивный план. Отдельная форма плана в UI удалена.

**Последствия.** Весь диалог о задаче идёт через чат, план появляется только
после достаточных ответов, а состояние задачи остаётся неизменным до этого
момента.


## DEC-039 · Единая точка входа — поле чата

**Дата:** 2026-11-18 · **Статус:** принято

**Контекст.** Утверждение плана и другие переходы были отдельными кнопками
панели состояния; пользователь просил единый вход и утверждение плана в чате.

**Решение.** Панель состояния стала только визуализацией. Все действия
задаются командами в поле чата: `/approve`, `/start`, `/complete`, `/validate`,
`/pass`, `/fail`, `/finish`, `/rework`, `/pause`, `/resume`. Утверждение плана
также принимается фразой «утверждаю план». Поле ввода находится под окном чата
в обычном потоке страницы, а не фиксируется поверх него.

**Последствия.** У пользователя один ввод для постановки задачи, уточнений,
утверждения плана и управления жизненным циклом; сервер по-прежнему проверяет
каждое действие.


## DEC-040 · Один блок ввода и чат только во вкладке задачи

**Дата:** 2026-11-19 · **Статус:** принято

**Контекст.** При отправке длинного запроса Streamlit успевал отрисовать второй
блок ввода, а чат оставался видимым на вкладке «Лог агента».

**Решение.** Отправка формы ставит сообщение в очередь и обрабатывается до
отрисовки формы; во время запроса новый блок ввода не создаётся. Чат перенесён
внутрь вкладки «Состояние задачи», вкладка «Лог агента» содержит только журнал.

**Последствия.** В интерфейсе всегда один блок ввода; история и лог не
смешиваются.


## DEC-041 · История чата и сессия переживают обновление

**Дата:** 2026-11-19 · **Статус:** принято

**Контекст.** После обновления страницы пропадала история чата, а новая
Streamlit-сессия могла не найти созданную задачу.

**Решение.** Идентификатор сессии записывается в query-параметр `l13_session`
и восстанавливается при загрузке. Сообщения чата сохраняются в SQLite в таблице
`chat_message` с привязкой к `session_id` и `task_id`; API отдаёт историю через
`GET /api/chat/history`, а команды/сообщения можно дописывать через
`POST /api/chat/message`. Задачи, переходы и журнал уже хранятся в SQLite.

**Последствия.** После F5 восстанавливаются задача, её состояние, история
переходов, журнал и переписка; новые задачи не смешиваются со старыми.


## DEC-042 · Явный результат действия

**Дата:** 2026-11-19 · **Статус:** принято

**Контекст.** После утверждения плана пользователь видел только изменившееся
состояние и не понимал, действие ещё выполняется, завершилось или упало.

**Решение.** Команды перехода показывают спиннер «Применяю действие…», затем
явное сообщение об успехе с подсказкой следующего шага либо сообщение об ошибке
в чате и баннере. Результат также сохраняется в истории чата.

**Последствия.** Утверждение плана и остальные переходы имеют однозначный
статус: выполняется, выполнено или ошибка.


## DEC-043 · Прозрачное выполнение шагов плана

**Дата:** 2026-11-19 · **Статус:** принято

**Контекст.** После перехода в реализацию пользователь видел только смену
этапа и не понимал, что именно делает агент.

**Решение.** При старте реализации план разбирается на шаги и сохраняется в
`task_step`. В панели «Реализация по плану» видны прогресс, статусы и результаты
каждого шага. Команда `/step` выполняет следующий шаг через модель и сохраняет
результат; завершение реализации запрещено, пока есть невыполненные шаги.
Результаты шагов также попадают в чат, журнал и SQLite.

**Последствия.** Пользователь видит фактическую работу по каждому шагу и может
управлять реализацией, не теряя прозрачности.


## DEC-044 · Рассуждения и результаты без служебного JSON

**Дата:** 2026-11-19 · **Статус:** принято

**Контекст.** Результаты шагов были свёрнуты, а журнал показывал служебные
JSON-детали; пользователь не видел, что именно сделал агент на этапе.

**Решение.** Результаты шагов отображаются в панели реализации сразу, с

возвращает разделы «Что сделано / Как выполнено / Результат / Ограничения», без
скрытых chain-of-thought. Служебные JSON-детали из журнала убраны.

**Последствия.** Пользователь видит ход работы и ограничения по каждому шагу,
не разбирая технические структуры.


## DEC-045 · Без ссылок и взрослого контента

## DEC-046 · Контекст до `/gotask`

**Дата:** 2026-11-19 · **Статус:** принято

**Решение.** В UI утверждение плана (`утверждаю план` или `/approve`) выполняет
два серверных перехода: `approve_plan`, затем `start_execution`. Состояние
становится `execution`, создаются шаги плана.

**Последствия.** Одно действие пользователя переводит задачу к выполнению;

## DEC-048 · Автовыполнение шагов и интерактивный прогресс

**Дата:** 2026-11-19 · **Статус:** принято

**Контекст.** После запуска реализации шаги требовали ручной команды `/step`,
поэтому пользователь не видел выполнения и не мог наблюдать прогресс.

**Решение.** Шаги выполняются автоматически после перехода в `execution`.
UI показывает прогресс, статусы и результаты шагов, спиннер текущего шага и
кнопку остановки/продолжения автовыполнения. `/step` убран из пользовательских
команд; API шага остаётся внутренним. Завершение реализации по-прежнему требует
`/complete`.

**Последствия.** Пользователь видит ход выполнения без ручных команд и может
приостановить процесс, не теряя результаты.


## DEC-049 · Статусы в чате, детали над чатом

**Дата:** 2026-11-19 · **Статус:** принято

**Контекст.** Автовыполнение писало в чат полные результаты шагов, из-за чего
история превышала лимит 4000 символов и чат становился перегруженным.

**Решение.** В чат пишутся только краткие статусы шагов («выполняется»,
«выполнен», «ошибка»); полные результаты остаются в блоке «Реализация по плану»
над чатом. План тоже отображается над чатом. История сообщений ограничивается
20 000 символов на сообщение и обрезается перед отправкой.

**Последствия.** Чат остаётся читаемым, детали доступны рядом, ошибка
`validation_error` по длине сообщения больше не возникает.


## DEC-050 · Ожидаемое действие — в чате

**Контекст.** Ожидаемое действие было видно только в панели состояния, хотя
всё управление задачей происходит в чате.

**Решение.** В окне чата выводится строка «Ожидается от вас: …» с текущим

`/resume` и т. п.). Для этапа планирования без плана — «ответить на уточняющие
вопросы».

**Последствия.** Пользователь видит следующий шаг прямо в чате и не ищет его
в панели состояния.

**Дата:** 2026-11-19 · **Статус:** принято

**Контекст.** После завершения шагов задача оставалась в `execution` с ожиданием

**Последствия.** Переход к валидации происходит сразу, возврат по модели

**Дата:** 2026-11-19 · **Статус:** принято

повторялось под списком шагов, а блок «Следующее действие» повторял
ожидаемое действие из шапки.

**Решение.** План показывается только в expander; в чате остаётся короткое
сообщение о готовности плана. Статусы шагов в чате не повторяют названия и
результаты — они находятся в expander шага. Блок «Следующее действие»
удалён, история переходов остаётся отдельным expander.

**Последствия.** На каждом этапе каждый блок отрисовывается один раз.


## DEC-059 · Валидация после интерактивного таймера

**Дата:** 2026-11-19 · **Статус:** принято

**Контекст.** После последнего шага валидация стартовала сразу, и ожидание
решения пользователя на этапе валидации было непрозрачным.

**Решение.** API завершает реализацию, но не запускает валидацию. UI показывает
интерактивный отсчёт 10 секунд с кнопкой «Запустить валидацию сейчас»; по
истечении отсчёта вызывает `start_validation`. На этапе валидации явно
показано ожидаемое решение `/pass` или `/fail`.

**Последствия.** Переход в валидацию виден и управляем; пользователь понимает,
что от него требуется.


## DEC-060 · Ошибки шага с причиной и лечением

**Дата:** 2026-11-19 · **Статус:** принято

**Контекст.** При пустом ответе модели шаг падал с общим сообщением
«Модель не вернула результат шага», без причины и рекомендаций.

**Решение.** Клиент OpenCode Go в строгом режиме бросает `LLMError` с кодом
(HTTP, сеть, пустой content, ключ), причиной и подсказкой. API передаёт
`hint` в `TaskError`; UI показывает текст ошибки и блок «Как исправить».
Для шага увеличен лимит токенов, пустой ответ повторяется с `max_tokens=4096`.

**Последствия.** Пользователь видит, что именно случилось и что сделать;
ошибка попадает в лог агента.


## DEC-061 · Автозавершение после успешной валидации

**Дата:** 2026-11-19 · **Статус:** принято

**Контекст.** После `/pass` требовалась ещё команда `/finish`, хотя этап
валидации уже завершён.

**Решение.** `/pass` сразу переводит задачу в `done` на сервере. Команда
`/finish` убрана из пользовательского списка и таблицы команд; на этапе
валидации ожидаются только `/pass` или `/fail`.

**Последствия.** Пользователь не делает лишний переход; финальный статус
наступает автоматически.


## DEC-062 · Очистка данных в сайдбаре

**Дата:** 2026-11-19 · **Статус:** принято

**Контекст.** Для сброса урока 13 приходилось обращаться к API или SQLite вручную.

**Решение.** В сайдбаре урока 13 добавлены кнопки «Очистить задачи» и
«Очистить чат» с обязательным подтверждением. API получил
`DELETE /api/task` (полный сброс) и `DELETE /api/chat/history` (только чат).

**Последствия.** Очистка доступна из интерфейса и не требует ручных запросов.
